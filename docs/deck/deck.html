Team and project introduction1
The developer problem

Every developer inherits code they did not write.

  • A small Flask + SQLite task API, new to the person who now owns it.
  • One behaviour is silently wrong: overdue tasks never show up.
  • One requirement is unbuilt: filtering tasks by tag.
  • No user interface, no release process, no project tooling.

Question: can IBM Bob take a developer from zero context to a diagnosed fix, new features, reviewed changes and a deployable product, with every step checkable?

Why this use case

Onboarding onto brownfield code is where developers lose the most time: reading unfamiliar structure, finding a cause rather than a symptom, and changing things without breaking what already works. That is exactly where an AI engineering partner has to earn trust.

Project introduction2
Starting point

A verifiable baseline, tagged before Bob saw it

  • Git tag pre-bob-baseline, pushed to GitHub before Bob's first prompt.
  • 4 tests, 3 passing; GET /tasks/overdue returned nothing for past-due tasks.
  • No ?tag= filter, JSON API only.

Disclosure

The starter was generated with Claude Code for this exercise and contained one deliberately seeded defect and the unbuilt filter. Bob was never told the answer. At the participant's direction, Claude Code also operated the Bob sessions: it wrote the prompts, handled Bob's approval requests and checked every stage independently, reporting only observed failures back to Bob. Every code change after the tag was made by IBM Bob.

Every Bob session is exported in the repository under bob_sessions/ (31 task records with Bob task ids), so each claim in this deck can be traced to a prompt, Bob's answer and a commit.
Project summary3
How IBM Bob was used

Bob was the engineering workflow, not a bolt-on

Explore/init and an AGENTS.md project context; Plan mode walked the request lifecycle, data model and risk areas before any edit.
DiagnoseAgent mode ran the tests and traced the failure from assertion to schema without hints; Ask mode explained SQL NULL semantics and repair options.
Fix and buildAgent mode implemented plans milestone by milestone, running the suite and committing after each step.
Tooling Bob made3 project skills, a /verify-taskflow command, a read-only TaskFlow Reviewer mode and a regression-check hook via /configure-hooks.
ReviewSubagent reviews (4 axes, then 5 adversarial lenses), reviewer-mode runs and the IDE's built-in /review with the Findings panel.

Used in Bob IDE and Bob Shell: Agent, Plan and Ask modes, the custom reviewer mode, and the IBM i Database and IBM i Developer modes for exploratory portability questions.

Project summary4
Fix

What Bob diagnosed and repaired

The seeded defect

completed was stored as NULL, and completed = 0 is never true for NULL under SQL three-valued logic, so every new task vanished from the overdue list. Bob fixed the schema default, backfilled old rows, made inserts explicit, and proved it on databases created by the old schema.

Exact tag filtering

?tag=back must not match backend. Bob matched whole tokens and escaped LIKE wildcards after a failure was reported (a_b matched axb).

Found by reviews

Unbounded error reflection, a 500 on oversized ids in PATCH, foreign keys switched off after schema setup, a keyboard trap in the edit dialog, missing security headers.

Concurrency

Simultaneous completions wrote duplicate history rows (109 of 200 trials). Bob's first fix did not hold; with the measurement in hand it switched to compare-and-swap updates: 0 of 200.

Project summary5
Build

What Bob built on top

  • Team task board UI: summary cards, filters, create, edit and complete; ES modules, keyboard accessible, responsive, dark mode.
  • Task lifecycle: open, in progress, blocked, completed; disallowed transitions return 409.
  • Activity history: an immutable timeline per task, with a non-destructive upgrade for databases from earlier versions.
  • Release: WSGI entry point, /health, a 22-check smoke test, PythonAnywhere deployment guide, GitHub Actions CI.

Project summary7
Future roadmap

Learnings, room for improvement, next steps

Key learnings

  • Bob found the root cause without hints and reasoned carefully about migrations.
  • Verify Bob's fixes by measuring them: two fixes looked right but failed until Bob saw the evidence.
  • Bob-made skills, a command, a mode and a hook made later work faster and checkable.

Room for improvement

  • No authentication or team workspaces yet.
  • SQLite suits one worker; scaling out needs Postgres.
  • No pagination or search in the board.

Next steps

  • Accounts and workspaces, pagination and search, a Postgres option, overdue notifications.
