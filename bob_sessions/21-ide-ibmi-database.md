## 1. `AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`

**SQLite ([`db.py:9,14`](app/db.py:9))**
```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
```

**Db2 for i**
```sql
id INTEGER NOT NULL GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1)
    CONSTRAINT users_pk PRIMARY KEY
```
`AUTOINCREMENT` is a SQLite keyword. Db2 for i uses the SQL-standard `GENERATED ALWAYS AS IDENTITY` (or `GENERATED BY DEFAULT AS IDENTITY` if you want to allow explicit inserts).

---

## 2. `TEXT` column type → `VARCHAR` / `DATE` / `SMALLINT`

**SQLite ([`db.py:10,15-22`](app/db.py:10))**  
SQLite is dynamically typed — `TEXT`, `INTEGER`, `REAL`, `BLOB`. Every column effectively accepts any value.

**Db2 for i** uses fixed types. The mapping for each column:

| SQLite column | Db2 for i type | Notes |
|---|---|---|
| `name TEXT NOT NULL` | `VARCHAR(100) NOT NULL` | matches `MAX_NAME_LENGTH = 100` |
| `title TEXT NOT NULL` | `VARCHAR(200) NOT NULL` | matches `MAX_TITLE_LENGTH = 200` |
| `description TEXT NOT NULL DEFAULT ''` | `VARCHAR(2000) NOT NULL DEFAULT ''` | matches `MAX_DESCRIPTION_LENGTH = 2000` |
| `tags TEXT NOT NULL DEFAULT ''` | `VARCHAR(373) NOT NULL DEFAULT ''` | 10 tags × 32 chars + 9 commas = 329; give it headroom |
| `due_date TEXT` | `DATE` | store as a native `DATE`; Db2 for i can then use date arithmetic directly (see §6) |
| `completed INTEGER NOT NULL DEFAULT 0` | `SMALLINT NOT NULL DEFAULT 0` | boolean flag; Db2 for i has no `BOOLEAN` in all contexts; `SMALLINT` is idiomatic |
| `created_at TEXT NOT NULL` | `TIMESTAMP NOT NULL` | store as `TIMESTAMP` rather than a string; use `CURRENT_TIMESTAMP` as default |

## 3. `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`

**SQLite ([`db.py:8,13,24`](app/db.py:8))**
```sql
CREATE TABLE IF NOT EXISTS users ( ... );
CREATE INDEX IF NOT EXISTS idx_tasks_assignee_id ON tasks (assignee_id);
```

**Db2 for i**  
`IF NOT EXISTS` on `CREATE TABLE` is supported from IBM i 7.3 TR9 / 7.4 TR3 onward (via SQL99 DDL extension). On older releases you must check [`QSYS2.SYSTABLES`](https://www.ibm.com/docs/en/i/7.5?topic=views-systables) first or wrap the DDL in a procedure that catches `SQLSTATE 42710`. For the index, `CREATE INDEX IF NOT EXISTS` is **not** supported at any release — use a `BEGIN … END` block that catches `SQLSTATE 42710` (object already exists), or query `QSYS2.SYSINDEXES` before creating.

## 4. `PRAGMA foreign_keys = ON` → no equivalent needed

**SQLite ([`db.py:32`](app/db.py:32))**
```python
conn.execute("PRAGMA foreign_keys = ON")
```

**Db2 for i**  
Foreign-key enforcement is always on. The `REFERENCES users (id)` constraint on [`db.py:19`](app/db.py:19) is enforced automatically — no per-connection pragma is needed.

## 5. `conn.executescript(SCHEMA)` → individual statements or a compound SQL block

**SQLite ([`db.py:58`](app/db.py:58))**
```python
conn.executescript(SCHEMA)
```
`executescript` is a `sqlite3`-specific method that executes a semicolon-separated block of statements.

**Db2 for i**  
Use `ibm_db` or `pyodbc` and execute each DDL statement individually, or wrap them in a `BEGIN … END` compound statement. There is no `executescript` equivalent in any Db2 Python driver.

## 6. `cursor.lastrowid` → `SELECT IDENTITY_VAL_LOCAL()`

**SQLite ([`services.py:43,67`](app/services.py:43))**
```python
cursor = db.execute("INSERT INTO users (name) VALUES (?)", (name,))
return {"id": cursor.lastrowid, "name": name}

cursor = db.execute("INSERT INTO tasks (...) VALUES (...)", ...)
return get_task(cursor.lastrowid)
```

**Db2 for i**  
`cursor.lastrowid` is a `sqlite3` cursor attribute with no direct equivalent in `ibm_db`/`pyodbc`. After an `INSERT` into an identity column use the SQL scalar function immediately after:

```sql
SELECT IDENTITY_VAL_LOCAL() FROM SYSIBM.SYSDUMMY1
```

Or use `INSERT … RETURNING` (supported from IBM i 7.5):
```sql
INSERT INTO users (name) VALUES (?) FETCH FIRST 1 ROWS ONLY
    -- not available; use IDENTITY_VAL_LOCAL() instead on older releases
```

The safe pattern for all supported releases:
```python
db.execute("INSERT INTO users (name) VALUES (?)", (name,))
row = db.execute("SELECT IDENTITY_VAL_LOCAL() AS id FROM SYSIBM.SYSDUMMY1").fetchone()
new_id = int(row["id"])
```

## 7. String concatenation `||` — no change needed

**SQLite ([`services.py:102`](app/services.py:102))**
```sql
(',' || tags || ',') LIKE ('%,' || ? || ',%') ESCAPE '\\'
```

**Db2 for i**  
The `||` concatenation operator is ANSI SQL and is fully supported in Db2 for i. This part does **not** need to change.

---

## 8. `LIKE … ESCAPE` — syntax is compatible, but the escape character literal differs

**SQLite ([`services.py:102`](app/services.py:102))**
```sql
LIKE ('%,' || ? || ',%') ESCAPE '\\'
```
In Python the string `'\\'` becomes the single character `\`, so the SQL sent to SQLite is:
```sql
LIKE ('%,' || ? || ',%') ESCAPE '\'
```

**Db2 for i**  
`LIKE … ESCAPE` is standard SQL and supported identically. The one subtlety: Db2 for i's default string delimiter is `'`; a single backslash literal is `'\'` — exactly the same as what SQLite receives. No change is needed to the SQL text itself. However, the Python-side escape logic in [`services.py:101`](app/services.py:101) (`tag.replace("\\", "\\\\")…`) is correct and carries over unchanged.

## 9. Date comparison in the overdue query → use `DATE()` cast or native `DATE` column

**SQLite ([`services.py:127`](app/services.py:127))**
```sql
WHERE due_date < ? AND completed = 0
```
This works in SQLite because `due_date` is stored as `TEXT` in `YYYY-MM-DD` form and SQLite does lexicographic comparison, which happens to be correct for ISO dates.

**Db2 for i**  
If `due_date` stays `VARCHAR` the same string comparison works (lexicographic order is identical for `YYYY-MM-DD`). But if you migrate it to the native `DATE` type (recommended, see §2), the bound parameter `today.isoformat()` (e.g. `'2025-07-15'`) must be cast:

```sql
WHERE due_date < DATE(?) AND completed = 0 ORDER BY due_date, id
```

Or pass a `datetime.date` object directly if the driver supports it (both `ibm_db` and `pyodbc` do for `DATE` columns). The Python call in [`services.py:128`](app/services.py:128) becomes:
```python
(today,)   # pass the date object, not today.isoformat()
```

## 10. Parameter markers `?` → `?` (pyodbc) or `%s` (ibm_db_dbi)

**SQLite ([`services.py:42,64,74,118,127,215`](app/services.py:42))**
```sql
VALUES (?, ?, ...)
WHERE id = ?
```

**Db2 for i**  
- **`pyodbc`** uses `?` — **no change needed**.  
- **`ibm_db_dbi`** (the IBM-supplied DB-API 2.0 wrapper) uses `?` as well — **no change needed**.  
- **`ibm_db`** (lower-level) uses `?` in `ibm_db.execute()` — **no change needed**.

All three common Db2 for i Python drivers use positional `?` markers, so every parameterised query in `services.py` is already compatible.

## 11. `conn.executescript` / startup backfill → execute individually + handle `SQLSTATE`

**SQLite ([`db.py:58-62`](app/db.py:58))**
```python
conn.executescript(SCHEMA)
with conn:
    conn.execute("UPDATE tasks SET completed = 0 WHERE completed IS NULL")
```

**Db2 for i**  
Two changes:

1. Replace `executescript` with individual `execute` calls (one per DDL statement).  
2. The backfill `UPDATE` itself is valid Db2 for i SQL — `WHERE completed IS NULL` on a `SMALLINT NOT NULL DEFAULT 0` column is a harmless no-op on a fresh database, identical to the SQLite behaviour. No change to the SQL text.

---

## 12. `with db:` transaction context manager → `ibm_db_dbi` / `pyodbc` connection context

**SQLite ([`services.py:41,61,117`](app/services.py:41))**
```python
with db:
    cursor = db.execute(...)
```
`sqlite3` connections act as transaction context managers: `__exit__` commits on success, rolls back on exception.

**Db2 for i**  
- `pyodbc` connections support the same `with conn:` context manager protocol (commit/rollback).  
- `ibm_db_dbi` connections also support it.  
So the `with db:` pattern is portable — **no change needed** as long as `autocommit` is `False` (the default).
